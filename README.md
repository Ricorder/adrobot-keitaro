# Adrobot — обёртка над Keitaro

Две части задания: **создаватор** кампаний (название + гео + ID оффера → кампания с двумя
потоками, доменом, группой и источником) и **редактор** существующей кампании (добавлять и
удалять офферы в потоке, доли пересчитываются, публикация в трекер — отдельной кнопкой).

Стек: FastAPI + SQLAlchemy + Alembic на бэкенде, React + Vite на фронтенде.

## Требования

- Python 3.11+ (проверено на 3.12.7)
- Node.js 20+ и pnpm (проверено на node v26.5.0, pnpm 12.9.1)
- Доступ к Keitaro: адрес трекера и API-ключ

## Быстрый старт

### Бэкенд

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env          # и вписать KEITARO_API_KEY
alembic upgrade head          # миграции
uvicorn app.main:app --reload --port 8000
```

Проверить, что поднялось:

```bash
curl -s localhost:8000/healthz     # {"status":"ok","database":"reachable","tables":10}
curl -s localhost:8000/api/meta    # префикс, адрес трекера, задан ли ключ
```

Документация API: http://localhost:8000/docs

### Фронтенд

```bash
cd frontend
pnpm install
pnpm dev                        # http://localhost:5173, /api проксируется на :8000
```

Сборка статики для проверки типов и продакшена:

```bash
pnpm exec tsc --noEmit
pnpm run build
```

## Демо-режим без стенда Keitaro

Если доступа к трекеру нет (или он закрыт), поднимается мок: `backend/tools/mock_keitaro.py`.
Это не часть приложения, а инструмент разработки — отдельный процесс, заменяющий
`KEITARO_BASE_URL`.

```bash
cd backend

# терминал 1: мок-трекер
uvicorn tools.mock_keitaro:app --port 8099

# терминал 2: бэкенд на моке и отдельной демо-базе
export DATABASE_URL=sqlite:///./demo.db
export KEITARO_BASE_URL=http://127.0.0.1:8099
export KEITARO_API_KEY=mock-key
alembic upgrade head
uvicorn app.main:app --port 8000

# терминал 3: фронтенд
cd ../frontend && pnpm dev
```

Мок намеренно повторяет не только успешные ответы, но и неудобные частности настоящего стенда
(сняты запросами к `tlgk.host`): голый массив без `total` в списке кампаний, `403 You have no
permission` на создание источника, домена и оффера, `401` на неверный ключ, `404` в виде
`{"error": ..., "stacktrace": null}`. Демо поэтому показывает то же поведение, что и боевой
прогон, а не упрощённую версию.

В моке четыре оффера (18813-18816), так что воспроизводится сценарий из демонстрации «четыре
оффера по 25 %», недоступный на реальном стенде: там один оффер, а создавать новые запрещено
правами ключа.

Сброс демо-состояния: остановить бэкенд, `rm backend/demo.db`, заново `alembic upgrade head`.
Мок хранит состояние в памяти и обнуляется перезапуском.

## Миграции

Схема живёт в `backend/app/db/models.py`, миграции — в `backend/migrations/versions/`.

```bash
cd backend
alembic upgrade head                    # накатить схему
alembic downgrade -1                    # откатить одну миграцию
alembic revision --autogenerate -m "что изменили"   # создать новую после правки моделей
alembic current                         # какая версия сейчас
```

По умолчанию база SQLite (`DATABASE_URL=sqlite:///./adrobot.db`) — чтобы проект запускался
без внешнего сервера. Для Postgres:

```bash
pip install -e ".[postgres]"
export DATABASE_URL=postgresql+psycopg://user:pass@localhost:5432/adrobot
alembic upgrade head
```

Схема проверена на обеих СУБД: `alembic upgrade head` проходит и на SQLite, и на локальном
PostgreSQL 18 (включая самозаполнение `stream_offers.id` на Postgres — там колонка
`nextval(...)`, а на SQLite `INTEGER PRIMARY KEY`).

## Конфигурация

Все значения — из `.env` (файл в `.gitignore`, в репозиторий не попадает).

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `DATABASE_URL` | `sqlite:///./adrobot.db` | база обёртки |
| `KEITARO_BASE_URL` | `https://tlgk.host` | адрес трекера |
| `KEITARO_API_KEY` | пусто | Профиль → API ключи; без него часть запросов отдаёт 503 |
| `KEITARO_PREFIX` | `kolesnikov-` | префикс названий кампаний и alias |
| `KEITARO_GROUP_NAME` | `FORTESTS` | группа кампаний: берётся существующей |
| `KEITARO_SOURCE_NAME` | `FORTESTS` | источник трафика: только переиспользуется |
| `KEITARO_TIMEOUT_SECONDS` | `15` | таймаут запроса к трекеру |
| `KEITARO_MAX_RETRIES` | `3` | повторы только сетевых ошибок и 5xx |
| `GOOGLE_REDIRECT_URL` | `https://www.google.com` | куда ведёт гео-поток |

Права тестового ключа проверены запросами: `POST /groups` разрешён, а `POST /traffic_sources`,
`POST /domains` и `POST /offers` отвечают `403 You have no permission`. Поэтому обёртка не
пытается создавать источник, домен или оффер, а переиспользует существующее и внятно ошибается,
если выбранного имени нет.

## Как выполняется часть 1 (создаватор)

`POST /api/campaigns` с телом `{name, geo, offer_id}` делает ровно то, что требует ТЗ:

1. `POST /campaigns` — `alias` (транслитерация названия + суффикс), `name`, `type: position`,
   `domain_id`, `group_id`, `traffic_source_id`;
2. `POST /streams` — гео-поток: `schema: redirect`, `action_type: http`,
   `action_options.url = GOOGLE_REDIRECT_URL`, `filters: [{name: "country", mode: "accept",
   payload: [GEO]}]`, позиция 1;
3. `POST /streams` — офферный поток: `schema: landings`, `offers: [{offer_id, share: 100}]`,
   позиция 2.

Значения `schema`/`action_type` взяты не из догадок: `GET /stream_schemas` отдаёт
`landings | redirect | action`, где `landings` называется «Landing pages & offers», а
`GET /streams_actions` — 18 действий, из них `http` это 302-редирект.

Дополнительно к ТЗ:

- **гео проверяется по ISO 3166-1 alpha-2** (249 кодов). У Keitaro нет эндпоинта стран, а
  опечатка в фильтре создала бы поток, который никогда ни с кем не совпадёт, — трекер на такое
  не жалуется;
- **идемпотентность**: заголовок `Idempotency-Key` или повторное название не создают вторую
  кампанию, а доделывают существующую;
- **компенсация**: если второй поток создать не удалось, первая кампания удаляется.

## Как выполняется часть 2 (редактор)

Логика повторяет показанный в демо инструмент, а не «PUT на каждый клик»:

| В демо | Реализация |
| --- | --- |
| Кнопка F-Streams забирает потоки | `GET /api/campaigns/{id}` подтягивает потоки из трекера в зеркало |
| Потоки без офферов не парсятся | показываются как есть, `offers: []`, без пересчётов |
| Добавить: ID → поиск → выбрать → Добавить | `GET /api/offers?q=` (по зеркалу, при пропуске один живой запрос), затем `POST /api/streams/{id}/offers` |
| После добавления веса пересчитаны (4 → по 25 %) | `app/services/weights.py`: сумма ровно 100 %, остаток от деления раздаётся по единице первым |
| Поток пожелтел — не опубликовано | `yellow = has_unpublished_changes`, локальные доли не затираются при повторном F-Streams |
| Remove → оффер сереет, доля 0 % | `DELETE /api/streams/offers/{row_id}` помечает `pending_remove`, строка живёт до публикации |
| После публикации оффер исчезает из Keitaro, но остаётся в архиве | `POST /api/streams/{id}/push` отправляет только живые связки, помеченные строки убираются из зеркала |
| Кнопка Back | `POST /api/streams/offers/{row_id}/restore` |
| Удалили в Keitaro, в обёртке тоже сереют | `mirror.sync_streams` помечает отсутствующие связки `removed_externally` с долей 0, а не удаляет их |
| Закрепленный вес не меняется, остальные делят остаток | `PUT /api/streams/offers/{row_id}/pin` + тот же пересчёт |

Зеркало отслеживает и исчезновение: `sync_campaigns` обходит все страницы списка кампаний,
поэтому отсутствие трактуется как удаление в трекере (`state: deleted`), а не как пропуск.

Единственная операция, которая пишет в трекер, — Push KT. До неё правки существуют только в
нашей базе, поэтому оброненная сессия ничего не ломает на общем стенде.

Если остались только закрепленные доли (например, 30 %), а свободные офферы удалены, сумма не
доходит до 100 % — это не молча доливается, а показывается как `unassigned_percent`, потому что
менять закрепление за пользователя обёртка не вправе.

## Структура

```
backend/
  app/
    config.py            настройки из окружения
    main.py              приложение и карта ошибок (400 / 404 / 502 / 503 / 504)
    deps.py              сессия и клиент Keitaro как зависимости
    api/                 HTTP-слой: создаватель, редактор, поиск офферов
    keitaro/client.py    REST-клиент: Api-Key, повторы, пагинация
    services/
      creator.py         часть 1: кампания + два потока, компенсация, идемпотентность
      editor.py          часть 2: добавить / убрать / вернуть / закрепить / опубликовать
      weights.py         пересчёт долей
      mirror.py          зеркало сущностей Keitaro и разрешение конфликтов
      geo.py, slug.py    валидация стран и транслитерация alias
  migrations/            Alembic
  tests/                 87 тестов
  tools/mock_keitaro.py  офлайн-мок трекера для демо и сквозных тестов
docs/keitaro-admin-api.json  OpenAPI-спека Keitaro, по которой написан клиент
frontend/                React + Vite
```

## Как проверялось

### Состояние тестового стенда на 23.11.2026

`tlgk.host` закрыт HTTP Basic-аутентификацией: запросы к `/admin/` и `/admin_api/v1/` отвечают
`403` с заголовком `www-authenticate: Basic realm="restricted"`, при этом корень домена отдаёт
`404` от nginx — сервер жив, закрыт именно доступ к API. 20 ноября те же запросы с тем же ключом
работали, живой прогон приведён ниже. Пользовательская пара для Basic-аута не выдаётся, поэтому
проверить обёртку на живом трекере сейчас нельзя; для проверки поднимается мок (раздел
«Демо-режим без стенда Keitaro»).

Код приложения от этого не зависит: в `backend/app/` нет ни одного упоминания мока или порта
8099, переключается только переменная `KEITARO_BASE_URL`. Мок — отдельный процесс в
`backend/tools/`, и он же используется сквозными тестами.

Что реально выполнено, а не «должно работать»:

- `pytest` — 87 тестов: модель, HTTP API, клиент (на `httpx.MockTransport`), пересчёт весов,
  зеркало, создаватель с отказами трекера, транслитерация и страны. Отдельный тест следит,
  чтобы в русские строки не попали иероглифы.
- Сквозные тесты против мок-трекера по loopback (`tests/test_mock_integration.py`): наш клиент
  и сервисы работают с сервером, который отвечает формами настоящего Keitaro, включая отказ
  на неверный ключ и 403 на создание источника и домена.
- Полный сценарий через HTTP и фронтенд-прокси прогнан скриптом: синк → создание кампании →
  добавление трёх офферов (по 25 %) → закрепление 40 % → удаление → Back → Push KT, и сверка
  долей напрямую в трекере, а не в нашем зеркале. Этот прогон и нашёл два дефекта: зеркало
  плодило дубли строк, когда трекер перевыпускал id связок, а `Back` возвращал ещё не
  опубликованный оффер в состояние «синхронизирован» без id.
- `ruff check` и `ruff format` — чисто.
- Миграции накатаны заново на SQLite и на PostgreSQL 18.
- **Живой прогон на `tlgk.host`** (ключ из ТЗ): кампания `Лив тест PR` создалась как
  id 216597, alias `kolesnikov-liv-test-pr-e78612`, `group_id 10332`, `traffic_source_id 836`,
  `domain_id 1813`; `GET /campaigns/216597/streams` прямо в трекере показал гео-поток
  (`redirect`, `http`, фильтр `country accept [AU]`) и офферный (`landings`, `18813` share 100).
  Дальше в редакторе: закрепление доли, попытка опубликовать поток без офферов (отказ с
  внятным текстом), возврат оффера и Push KT — `shares {"18813": 100}`, поток снова не жёлтый.
  Проверочная кампания удалена, на стенде от неё ничего не осталось (ни кампаний,
  ни групп, ни офферов с префиксом `kolesnikov-`). Повторный `POST /api/sync` показал,
  что зеркало помечает её `state: deleted`, а не держит вечно активной — этот случай
  отдельно найден живой проверкой и закрыт тестом.
- Чужие реальные данные: открыли кампанию 216370 с тремя офферами — редактор показал
  34/33/33 % и «не распределено 0 %», имена отсутствующих в справочнике офферов подписаны
  как `оффер <id>`.

Чего проверить не удалось, и почему:

- **Клик по трекинг-URL.** Домен стенда `kylovoa.com` не имеет DNS-записей (`dig +short` пустой),
  поэтому реальный редирект наблюдением не подтвердить — конфигурация проверена через API.
- **Добавление второго оффера вживую.** Создание офферов закрыто правами ключа (403), на стенде
  ровно один оффер. Сценарий «4 оффера по 25 %» покрыт тестами, а не прогоном.
- **Сохраняет ли `PUT /streams` id связок поток-оффер.** Стенд закрылся раньше, чем это удалось
  проверить, а поведение влияет на зеркало: если трекер перевыпускает id при каждой публикации,
  сопоставление только по `link_id` породило бы дубли строк. Зеркало опознаёт строку по паре
  «поток + оффер», поэтому корректно работает при обоих вариантах; оба поведения покрыты
  тестами (`test_push_keeps_row_identity_when_tracker_reissues_link_ids`).
- **Поведение на реальном трафике.** Задержки, таймауты, 5xx и лимиты частоты запросов мок не
  воспроизводит: он отвечает мгновенно и не ломается. Логика повторов с экспоненциальной
  задержкой проверена на `httpx.MockTransport`, а не на живой сети.
- **UI в браузере.** Фронтенд собирается и проходит `tsc --noEmit`; кликами в браузере
  нужно проверить самому: `pnpm dev` поднимется на :5173 и проксирует `/api` на бэкенд.

## Ошибки и коды возврата API

| Ситуация | HTTP |
| --- | --- |
| Неверные данные или правило обёртки (гео, дубль оффера, пустой поток) | 400 с человекомочитаемым `detail` |
| Оффер не найден в трекере | 404 |
| Трекер отказал (4xx/5xx кроме выше) или вернул неожиданную структуру | 502 |
| Нет API-ключа | 503 |
| Нет связи с трекером | 504 |

`ValueError` в глобальный обработчик не включён намеренно: сервисы оборачивают свои ошибки в
`CreatorError` / `EditorError`, а перехват чужих исключений спрятал бы настоящие баги.

## CI

`.github/workflows/ci.yml` прогоняет линтер, тесты и сборку фронтенда на каждый push и PR.
Живого стенда в CI нет: ключ в репозитории не хранится, проверка на живом стенде сделана вручную и
описана выше.
