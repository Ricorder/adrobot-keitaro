# DEMO — как это работает, шаг за шагом

Вместо скринкаста: реальный прогон сценария с настоящими запросами и ответами. Снято
23.11.2026 через фронтенд-прокси (`localhost:5173` → бэкенд `:8000` → трекер), то есть это
не пересказ, а лог работающего приложения. JSON сокращён до полей, которые важны для шага;
полные ответы видны в `/docs` FastAPI на `http://localhost:8000/docs`.

Трекеров в этом прогоне два, и это принципиально:

- `:8000` — наше приложение (FastAPI + зеркало в SQLite);
- `:8099` — трекер Keitaro. В демо-режиме это `tools/mock_keitaro.py`; 20.11.2026 тот же
  сценарий выполнен на настоящем `tlgk.host` (кампания id 216597, подробности в README,
  раздел «Как проверялось»).

Чтобы повторить у себя: раздел «Демо-режим без стенда Keitaro» в README, три команды.

## Шаг 1. Синхронизация справочников

```
POST /api/sync
```

```json
{
  "campaigns": 3,
  "streams": 0,
  "offers_in_streams": 0,
  "reference": { "offers": 4, "groups": 2, "domains": 1, "traffic_sources": 1 }
}
```

Офферы, группы, домены и источники закачаны в наше зеркало. Потоки здесь не тянутся:
они подтягиваются по одной кампании, когда её открывают (это и есть кнопка F-Streams).

## Шаг 2. Создаватор: кампания из названия, гео и оффера

```
POST /api/campaigns
{ "name": "Демо PE", "geo": "PE", "offer_id": 18813 }
```

Ответ **201**:

```json
{
  "id": 900210,
  "alias": "kolesnikov-demo-pe-51cd92",
  "domain_id": 1813, "group_id": 10332, "traffic_source_id": 836,
  "streams": [
    { "id": 900211, "position": 1, "schema": "redirect", "action_type": "http",
      "action_options": { "url": "https://www.google.com" },
      "filters": [ { "name": "country", "mode": "accept", "payload": ["PE"] } ],
      "offers": [], "yellow": false },
    { "id": 900213, "position": 2, "schema": "landings",
      "offers": [ { "offer_id": 18813, "share": 100, "sync_status": "synced" } ],
      "yellow": false }
  ]
}
```

Ровно то, что требует задание: поток 1 ловит указанную страну и уходит на Google, поток 2
отдаёт выбранный оффер; домен, группа и источник проставлены. `alias` собран транслитерацией
названия с префиксом и случайным хвостом — уникальность гарантирована, а URL читаемый.

## Шаг 3. Редактор: добавляем три оффера

Три запроса `POST /api/streams/900213/offers` с `offer_id` 18814, 18815, 18816. Доли
пересчитываются на каждом шаге, сумма всегда 100 %:

| после добавления | 18813 | 18814 | 18815 | 18816 |
| --- | --- | --- | --- | --- |
| 1 оффер | 100 | — | — | — |
| 2 оффера | 50 | 50 | — | — |
| 3 оффера | 34 | 33 | 33 | — |
| 4 оффера | 25 | 25 | 25 | 25 |

Ответ на последнее добавление (сокращено):

```json
[
  { "offer_id": 18813, "share": 25, "sync_status": "synced",      "link_id": 900214, "yellow": true },
  { "offer_id": 18814, "share": 25, "sync_status": "pending_add", "link_id": null,   "yellow": true },
  { "offer_id": 18815, "share": 25, "sync_status": "pending_add", "link_id": null,   "yellow": true },
  { "offer_id": 18816, "share": 25, "sync_status": "pending_add", "link_id": null,   "yellow": true }
]
```

Три детали, которые видно в этом ответе:

- `yellow: true` — поток стал жёлтым: правки есть, но в трекер ещё не ушли;
- `link_id: null` у добавленных строк — идентификатора связки у трекера ещё нет, он появится
  после публикации. Поэтому у строки собственный локальный ключ `id`, а `link_id` отдельный;
- `sync_status` отличает «опубликовано» от «черновик», и именно по нему интерфейс красит строки.

100 % на троих не делится, поэтому остаток раздаётся по единице первым: 34/33/33, а не
33,33/33,33/33,34 — Keitaro работает с целыми процентами.

## Шаг 4. Закрепление доли

```
PUT /api/streams/offers/3/pin
{ "share": 40 }
```

Ответ **204**. Состояние потока после этого: 18814 держит 40 %, остальные делят 60 % → 20/20/20.
Закреплённый вес не участвует в пересчёте: ни добавление, ни удаление соседей его не сдвинет.

## Шаг 5. Remove и Back

```
DELETE /api/streams/offers/4      → 204
```

Оффер 18815 сереет (`grey: true`, `sync_status: pending_remove`), его доля становится 0,
а освободившиеся проценты уходят соседям: 18813 → 30, 18814 → 40 (закреплён), 18816 → 30.
Строка при этом **не удаляется** — она живёт в зеркале до публикации, поэтому её можно вернуть:

```
POST /api/streams/offers/4/restore   → 204
```

После возврата доли снова 20/40/20/20.

## Шаг 6. Push KT — единственная запись в трекер

```
POST /api/streams/900213/push
```

```json
{
  "streams": 2, "offers_in_streams": 4, "removed_externally": 0, "kept_pending": 0,
  "yellow": false,
  "shares": { "18813": 20, "18814": 40, "18815": 20, "18816": 20 }
}
```

`yellow: false` — черновик опубликован. До этого момента все правки жили только в нашей базе:
ни один запрос в трекер не уходил, и закрытая вкладка браузера ничего бы не сломала.

## Шаг 7. Контрольная сверка в обход нашего зеркала

Чтобы «верные цифры» не были словами, состояние потока снято напрямую у трекера, минуя
наше приложение:

```
GET http://127.0.0.1:8099/admin_api/v1/campaigns/900210/streams     (заголовок Api-Key)
```

```json
[
  { "id": 900211, "position": 1, "schema": "redirect", "action_type": "http",
    "action_options": { "url": "https://www.google.com" },
    "filters": [ { "id": 900212, "name": "country", "mode": "accept", "payload": ["PE"] } ],
    "offers": [] },
  { "id": 900213, "position": 2, "schema": "landings",
    "offers": [
      { "id": 900214, "offer_id": 18813, "share": 20, "state": "active" },
      { "id": 900216, "offer_id": 18814, "share": 40, "state": "active" },
      { "id": 900217, "offer_id": 18815, "share": 20, "state": "active" },
      { "id": 900218, "offer_id": 18816, "share": 20, "state": "active" }
    ] }
]
```

Трекер хранит ровно те доли, что показал интерфейс, сумма 100 %, гео-фильтр на месте.
Обратите внимание: у 18813 сохранился прежний `id` связки (900214), а у добавленных появились
новые (900216-900218). Зеркало обязано работать при любом из вариантов — сохраняет трекер
идентификаторы или перевыпускает их, — поэтому строки опознаются по паре «поток + оффер»,
а не только по `link_id`. Это не теория: на первой версии кода, которая сопоставляла только
по `link_id`, прогон показал дубли строк и ложно «удалённые в трекере» офферы.

## Шаг 8. Отказы — что видит пользователь

Неверный гео-код:

```
POST /api/campaigns  { "name": "Плохое гео", "geo": "XX", "offer_id": 18813 }
→ 400 { "detail": "неизвестный код страны ISO 3166-1 alpha-2: XX" }
```

Несуществующий оффер:

```
POST /api/campaigns  { "name": "Нет оффера", "geo": "PE", "offer_id": 999999 }
→ 400 { "detail": "оффер 999999 в Keitaro не найден: Keitaro 404 на /offers/999999: Offer not found" }
```

Публикация потока, из которого убрали все офферы:

```
POST /api/streams/{id}/push
→ 400 { "detail": "в офферном потоке не осталось ни одного оффера — Push KT не нужен" }
```

Ни один из этих случаев не оставляет на стенде половину кампании: если второй поток создать не
удалось, первая кампания удаляется, а запись в журнале говорит, что именно произошло.

## Что ещё стоит проверить руками

- **Повтор с тем же `Idempotency-Key`** не создаёт вторую кампанию, а возвращает существующую;
  повтор с тем же названием без ключа — тоже (иначе на общем стенде плодились бы копии).
- **Повтор с другим гео** при том же названии отклоняется с текстом «кампания уже ловит PE,
  а запрошено RU»: молча переписать чужой фильтр обёртка не имеет права.
- **Удаление оффера прямо в трекере** (в демо-режиме — руками через API) при следующем
  F-Streams даёт серый оффер с долей 0 и кнопку возврата, а не пропажу строки.
